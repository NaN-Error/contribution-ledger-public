# Your first practice session

The program runs in a browser. Start with fictional names and work. You do not need GitHub, AI keys or payment accounts.

## Open it

On the already prepared computer, double-click **Contribution Ledger** on your desktop (or Contribution Ledger.vbs beside the local quick-start guide). The startup window starts the saved installation and opens your browser. First use: click **Copy first-use setup code**, paste it into **Setup token** in the browser, and choose your own owner account. The code lasts one hour and can be used once. Later visits sign in normally; an existing signed-in browser session opens the repository dashboard directly. No terminal or separate token script is needed. Closing the startup window leaves the app running. Native launcher source is included; installed shortcuts, binaries and private state are computer-specific. Do not send codes or passwords in chat.

For a fresh installation from the source ZIP, follow [Start here](start_here.md): extract it, start Docker Desktop, double-click `Start-local.cmd`, run `scripts/setup-owner.ps1`, and open `http://127.0.0.1:5173`. That route needs Docker Desktop. A running prepared native instance may use a different address shown by its launcher.

Enter a display name, email, unique password of at least 15 characters, workspace name and first project name. Example workspace: **Practice team**. Example project: **Fictional game**. Use your project timezone; `America/La_Paz` is supported. No confirmation email is sent locally. Later visits use **Sign in**, without another setup token.

## First ten-minute check

For the repository-first workflow, open **Repository dashboard**, select your project and add a public GitHub URL. Choose dates covering known work. Open a contributor username and an outcome to inspect its evidence. Add a fictional extra contribution and propose units with a reason, then enter a hypothetical USD amount. Draft proposals do not issue credit. Private repositories still require the separate GitHub App setup; AI is optional. See [Repository contribution dashboard](../repository_analysis.md).

1. Open **Getting started**. Choose **New project or manual evidence first**.
2. Open **System overview**. Check that API and database respond.
3. Open **Workspaces**, your workspace and your project. Find **Settings and access** and **Team access**. Invite a separate fictional contributor and reviewer through **Invitations**. Open invitation links in a separate browser profile or private window so the accounts stay separate. Invitation links appear in the app; it does not send email.
4. Sign out and sign back in. Confirm that the workspace and project are still present.
5. Stop using the matching launcher, then start again and sign in. Confirm the same project remains. Closing the browser alone leaves the services running.

## First complete contribution

Follow the numbered **Getting started** steps and [the detailed checklist](testing_checklist.md). Approve a policy and have each required account acknowledge it. Approve a milestone budget, allocate work and create a work package with acceptance criteria and deliverables. Attach a fictional short report and submit it. Use the reviewer account for independent review, then finalize only the accepted portion.

Check **Contribution overview** for the credited person, units and visible percentage denominator. Repeat finalization to check that credit does not double. Try insufficient evidence and confirm it stays uncredited. Use **Revenue simulator** with fictional amounts after credit exists. Financial records remain synthetic-only.

For a first pass, keep one deliverable and a small budget so the result is easy to follow. Running multiple accounts yourself checks the software; it does not constitute an independent human pilot.

## Save a useful bug report

Write down the screen, exact clicks, expected result, actual result and any visible error or request ID. Keep the small fictional example. Do not reset saved data to hide an error, or send passwords, tokens, keys, private evidence or database dumps. Keep the project folder, database and encryption masters together when retaining the prepared local instance.
